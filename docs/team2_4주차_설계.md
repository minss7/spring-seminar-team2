## 1. 구현 범위

| 구분 | API | 처리 내용 | 대상  |
| --- | --- | --- |---|
| 기존 기능 개선 | `POST /seminars/{seminarId}/enrollments` | 정원 초과와 중복 신청 방지 | 와장, 승인된 루키 |
| 기존 기능 개선 | `DELETE /seminars/{seminarId}/enrollments/me` | 중복 취소 방지, 수강 신청과 연결된 기록 삭제 | 와장, 본인의 신청이 있는 승인된 루키 |
| 신규 | `GET /seminars/{seminarId}/dashboard` | 회차와 수강생별 운영 현황 조회 |  와장, 승인된 담당 운영진, 해당 세미나를 수강 중인 승인된 루키 |
| 신규 | `PATCH /seminars/{seminarId}/enrollments/{enrollmentId}` | 잔여 Grace Day와 탈락 여부 부분 수정 |  와장, 승인된 담당 운영진 |
| 신규 | `PATCH /sessions/{sessionId}/records` | 여러 수강생의 출석·과제 기록 일괄 수정 |  와장, 해당 회차가 속한 세미나의 승인된 담당 운영진 |

신청·취소의 요청 형식과 성공 응답은 기존 계약을 유지한다. 신청자는 요청 본문이 아니라 인증된 사용자의 `principal.id`로 식별한다. 신규 운영 API도 기존 인증 체계를 사용하며, 인증 실패는 `401`, 권한이 없는 요청은 `403`으로 처리한다.

## 2. 문제 상황과 원인

### 2.1. 정원 확인과 저장 사이의 경쟁 상태

정원 30명인 세미나에 이미 29명이 신청한 상황에서, 두 요청이 다음과 같이 실행될 수 있다.

| 순서 | 요청 A | 요청 B |
| --- | --- | --- |
| 1 | 현재 인원 29명 조회 | |
| 2 | | 현재 인원 29명 조회 |
| 3 | 여석이 있다고 판단하고 신청 저장 | |
| 4 | | 여석이 있다고 판단하고 신청 저장 |

최종 신청 수는 31명이 된다. 각 요청이 올바르게 인원을 계산했더라도, 조회한 상태가 저장 시점까지 유지되지 않으면 정원을 보장할 수 없다.

서비스에 `@Transactional`을 붙이는 것만으로는 이 경쟁 상태가 해결되지 않는다. 트랜잭션은 함께 반영하거나 되돌릴 작업의 범위를 정하지만, 다른 트랜잭션이 같은 인원을 읽고 신청하는 것까지 자동으로 차단하지는 않는다.

### 2.2. 중복 신청

같은 사용자의 두 요청이 모두 “아직 신청하지 않았다”는 조회 결과를 얻고 저장으로 진행할 수 있다.

현재 스키마에는 `UNIQUE(user_id, seminar_id)`가 있으므로 같은 사용자·세미나 조합의 중복 행은 DB에서도 방지한다. 다만 제약조건만으로 처리하면 저장 시점의 제약 위반을 처리해야 한다. 신청 흐름을 직렬화해 후속 요청이 기존 신청을 확인하고, 업무상 중복 요청으로 `409`를 반환하도록 했다.

### 2.3. 중복 취소

취소가 “신청 조회 → 삭제 → 성공 반환”으로만 구성되면, 여러 요청이 삭제 전의 같은 신청을 조회할 수 있다. 실제 삭제 건수를 확인하지 않는 구현에서는 한 요청만 행을 삭제했는데 여러 요청이 성공으로 응답할 수 있다.

이 프로젝트는 인원 집계 컬럼을 따로 저장하지 않는다. 중복 취소에서는 실제 신청이 한 번만 삭제되고, 응답도 `204` 한 건과 나머지 `404`로 구분되는지를 확인한다.

### 2.4. 신청과 취소의 혼합 실행

같은 세미나의 신청과 취소는 모두 수강 신청 집합을 변경한다. 두 흐름이 같은 잠금 규칙을 사용하도록 해, 각 요청이 앞선 작업의 커밋 이후 상태를 기준으로 검사하고 변경하게 했다.

다만 정원이 찬 상태에서 신청이 취소보다 먼저 처리되어 `409`를 반환하는 것은 허용된 동작이다. 이후 취소가 성공해 빈자리가 생겼다면 새로운 신청으로 그 자리를 채울 수 있어야 한다.

검증해야 하는 조건은 다음과 같다.

```text
최종 인원 = 초기 인원 + 신청 성공 수 - 취소 성공 수
0 ≤ 최종 인원 ≤ 정원
```

동시에 도착한 요청의 HTTP 도착 순서나 스레드 제출 순서까지 보장하지 않는다. 비관적 락은 같은 세미나의 변경을 순차 처리하기 위한 것이며, 별도의 선착순 대기열을 구현한 것은 아니다.

### 2.5. 여러 DB 변경 중 일부만 반영되는 문제

출석과 과제를 각각 저장하거나 여러 수강생을 수정할 때, 각 DB 작업이 별도로 커밋되면 앞선 변경 이후 예외가 발생했을 때 일부 기록만 남을 수 있다.

예를 들어 첫 번째 수강생의 출석 수정은 커밋되고, 다음 수강생의 과제 처리에서 예외가 발생하면 하나의 일괄 요청이 일부만 반영된다. 관련 변경 전체를 하나의 트랜잭션으로 묶어 이 상황을 방지한다.

## 3. 수강 신청·취소 동시성 제어

### 3.1. 문제 상황

수강 신청은 현재 인원을 조회한 뒤 정원에 여유가 있으면 신청 정보를 저장한다. 동시성 제어가 없다면 여러 요청이 같은 인원을 조회하고 각각 저장하여 정원을 초과할 수 있다.

동일 사용자의 중복 신청이나 취소도 문제가 된다. 여러 요청이 동시에 신청 내역의 존재 여부를 확인하면, 같은 신청을 여러 번 처리하려고 시도할 수 있다. 따라서 검사와 데이터 변경 전체를 하나의 보호 범위로 묶어야 한다.

### 3.2. 선택한 방식: 세미나 행의 비관적 락

MySQL의 `SELECT ... FOR UPDATE`를 사용하여 신청·취소 대상 세미나 행을 잠근다.

신청과 취소 모두 동일한 세미나 행을 먼저 잠그도록 구현했다. 같은 세미나에 대한 요청은 앞선 트랜잭션이 종료될 때까지 기다리며, 잠금을 획득한 이후 중복 여부와 인원을 조회한다.

세미나별로 잠금 대상이 구분되므로 서로 다른 세미나의 신청·취소를 하나의 공통 잠금으로 묶지 않는다.

### 3.3. 트랜잭션 범위와 처리 순서

신청과 취소 서비스 메서드에 `@Transactional`을 적용했다. 잠금은 트랜잭션의 커밋 또는 롤백까지 유지된다.

**수강 신청**

1. 사용자 권한을 확인한다.
2. 대상 세미나 행을 잠근다.
3. 기존 신청 여부를 확인한다.
4. 신청 기간과 현재 인원을 확인한다.
5. 정원이 남아 있으면 신청 정보를 저장한다.
6. 커밋 후 잠금을 해제한다.

**수강 취소**

1. 사용자 권한을 확인한다.
2. 신청과 동일한 세미나 행을 잠근다.
3. 본인의 신청 내역과 신청 기간을 확인한다.
4. 신청 정보를 삭제한다.
5. 커밋 후 잠금을 해제한다.

신청과 취소가 섞여 실행되더라도 같은 잠금을 사용하므로, 각 요청은 앞선 요청의 커밋 결과를 반영하여 처리한다.

### 3.4. 중복 요청과 데이터 정합성

중복 신청은 잠금 획득 후 기존 신청을 조회하여 `409 Conflict`로 처리한다. DB의 `(user_id, seminar_id)` 유니크 제약조건도 유지하여 중복 데이터 저장을 방지한다.

중복 취소에서는 첫 요청만 삭제에 성공한다. 이후 요청은 잠금 획득 후 신청 내역이 없음을 확인하고 `404 Not Found`를 반환한다.

현재 수강 인원은 별도 집계 컬럼 없이 실제 `enrollments` 행을 집계한다. 따라서 신청·취소와 별도로 인원 값을 증감하며 발생할 수 있는 불일치를 피한다.

취소 시 연결된 출석·과제 기록은 외래 키의 `ON DELETE CASCADE`로 함께 삭제된다. 삭제 작업은 같은 트랜잭션에 포함되므로 실패하면 함께 롤백된다. 재신청 시에는 새로운 신청 정보를 생성하여 Grace Day를 세미나 기본값으로, 탈락 여부를 `false`로 초기화한다.

### 3.5. 선택 이유와 한계

비관적 락은 충돌한 요청을 대기시킨 뒤 순서대로 처리할 수 있어, 정원이 남아 있는데 단순 충돌로 신청을 실패시키는 상황을 피하기 쉽다.

낙관적 락은 충돌 시 재시도 설계가 필요하고, 조건부 인원 증가 방식은 별도 집계 컬럼과 신청 정보의 일관성을 함께 관리해야 한다. 현재 구조에서는 세미나 행을 잠그는 방식이 변경 범위가 작고 처리 과정을 설명하기 쉽다고 판단했다.

같은 세미나에 요청이 집중되면 잠금 대기로 처리량이 제한될 수 있다. 따라서 잠금 획득 후에는 필요한 DB 작업만 수행하고 트랜잭션을 짧게 유지한다. 향후 신청 정보를 변경하는 경로를 추가할 때에도 동일한 잠금 규칙을 따라야 한다.

### 3.6. 검증 결과

기존 `EnrollmentConcurrencyApiTest`를 실행하여 통과했다. 해당 테스트로 다음 사항을 확인했다.

- 서로 다른 사용자의 동시 신청 시 정원만큼 정확히 성공한다.
- 마지막 남은 자리에 대해서만 신청이 성공한다.
- 동일 사용자의 중복 신청은 한 번만 성공하며 남은 자리를 추가로 소비하지 않는다.
- 중복 취소는 한 번만 성공하고, 이후 재신청할 수 있다.
- 신청과 취소가 섞여도 최종 인원이 다음 관계를 만족한다.

```text
최종 인원 = 초기 인원 + 신청 성공 수 - 취소 성공 수
0 ≤ 최종 인원 ≤ 정원
```

- 동시 작업 종료 후 세미나 조회, 내 수강 목록, 대시보드의 신청 정보와 인원·상태가 일치한다.

## 4. 운영 정보 수정과 트랜잭션 경계

### 4.1. 함께 성공하거나 실패해야 하는 작업

| 기능 | 서비스 메서드 | 하나의 트랜잭션에 포함되는 DB 작업 |
| --- | --- | --- |
| 수강 신청 | `EnrollmentService.enroll()` | 세미나 잠금, 중복·기간·정원 검사, 신청 저장 |
| 수강 취소 | `EnrollmentService.delete()` | 세미나 잠금, 신청·기간 확인, 신청 삭제와 FK에 따른 출석·과제 삭제 |
| 수강 정보 수정 | `EnrollmentService.patch()` | 세미나·신청·권한 확인, 수정 항목 전체 검증, 수강 정보 저장 |
| 출석·과제 일괄 수정 | `SessionRecordService.updateRecords()` | 요청 전체의 소속 검증, 모든 항목의 출석·과제 생성·수정·삭제 |

각 서비스는 Spring에서 주입받은 객체를 통해 호출한다. 기본 롤백 대상인 `RuntimeException` 또는 `Error`가 전파되면 해당 트랜잭션의 변경을 되돌린다. 일괄 수정 도중의 예외를 삼키고 성공으로 반환하지 않는다.

### 4.2. 취소 시 연결된 기록 정리

기존 스키마의 `attendances.enrollment_id`와 `submissions.enrollment_id`에는 `ON DELETE CASCADE`가 설정되어 있다. 신청을 삭제하면 연결된 기록도 같은 DB 트랜잭션에서 삭제된다.

다른 수강생의 기록과 세미나의 회차는 유지한다. 삭제 중 오류가 발생하면 해당 트랜잭션의 앞선 변경도 롤백된다.

취소 후 다시 신청하면 새로운 신청을 만들며, 잔여 Grace Day는 세미나의 `totalGraceDays`, 탈락 여부는 `false`로 시작한다. 삭제된 이전 신청의 기록을 복원하지 않는다.

### 4.3. 수강 정보 부분 수정

`PATCH /seminars/{seminarId}/enrollments/{enrollmentId}`는 와장과 해당 세미나의 승인된 담당 운영진만 사용할 수 있다.

- `enrollmentId`는 사용자 ID가 아닌 수강 신청 ID이다.
- 잔여 Grace Day는 `0..totalGraceDays` 범위의 정수만 허용한다.
- `dropped`는 boolean만 허용한다.
- 생략한 항목은 유지하고, 명시적인 `null`이나 수정할 항목이 없는 요청은 `400`으로 처리한다.
- 수강 신청이 경로의 세미나에 속하지 않으면 `404`로 처리한다.
- 두 항목을 모두 검증한 후 저장하므로 한 항목이 잘못되면 어느 항목도 반영하지 않는다.
- 신청 ID와 생성 일시, 출석·과제 기록은 변경하지 않는다.

Grace Day는 출석·과제 상태에 따라 자동 차감하지 않는다. 탈락 여부는 표시용 값으로, 신청을 삭제하거나 정원에서 제외하지 않는다. 운영 정보 수정은 신청 기간이 종료된 뒤에도 허용한다.

### 4.4. 출석·과제 일괄 수정

`SessionRecordService.updateRecords()`에 `@Transactional`을 적용했습니다. 한 일괄 요청에 포함된 출석·과제 기록의 생성, 수정, 삭제는 하나의 트랜잭션에서 처리됩니다.

저장 전에 요청에 포함된 수강 신청이 존재하는지, 해당 회차의 세미나에 속하는지 모두 검증합니다.

필드가 요청에 포함되었는지와 그 값을 구분한다.

| 요청 상태 | 처리 |
| --- | --- |
| 필드 생략 | 기존 기록 유지 |
| 허용된 상태 값 전달 | 기록이 없으면 생성, 있으면 수정 |
| 명시적 `null` 전달 | 해당 출석 또는 과제 기록 삭제 |
| 이미 미기록인 필드에 `null` 전달 | 정상 처리하며 미기록 유지 |

출석과 과제는 독립적으로 수정한다. 요청에 없는 수강생과 다른 회차의 기록, 잔여 Grace Day와 탈락 여부는 유지한다. 한 회차·수강 신청 조합의 출석과 과제가 각각 하나만 존재하도록 기존 UNIQUE 제약조건도 유지한다.

## 5. 대시보드 조회 설계

### 5.1. 조회 권한

| 사용자 | 조회 조건 |
| --- | --- |
| 와장 | 조회 가능 |
| 운영진 | `APPROVED`이고 해당 세미나의 담당 운영진 |
| 루키 | `APPROVED`이고 해당 세미나에 수강 신청이 남아 있음 |

루키도 같은 세미나의 다른 수강생 현황을 조회할 수 있다. 탈락 표시가 있어도 신청이 남아 있으면 조회 가능하며, 취소로 신청이 삭제되면 조회 권한을 잃는다.

세미나 존재 여부 확인과 권한 검사는 [SeminarService](../src/main/kotlin/com/wafflestudio/spring2026/seminar/service/SeminarService.kt)의 `getDashboard()`에서 수행한다. 페이지 번호·크기의 기본값과 범위 검사는 Controller에서 처리한다.

### 5.2. 데이터 조회와 응답 조립

Repository는 회차·수강 신청·사용자·출석·과제 데이터를 조회하고, Service가 대시보드 응답 DTO로 조립한다.

1. 세미나의 전체 회차를 `starts_at ASC, id ASC`로 조회하고 순서대로 `round`를 1부터 계산한다.
2. 해당 세미나의 신청을 `id ASC`로 정렬하고 수강생 행에만 페이지네이션을 적용한다.
3. 각 신청의 `userId`로 실제 수강생 정보를 조회한다. 조회 요청자인 `principal`을 각 행의 수강생 정보로 사용하지 않는다.
4. 각 수강생에 대해 전체 회차를 순회하며 출석·과제 기록을 연결한다.
5. 실제 신청 수로 `totalElements`를 계산하고, 페이지 크기로 나누어 올림한 값을 `totalPages`로 반환한다.

`sessions[].id`는 회차 ID, `content[].id`는 신청 ID, `content[].user.id`는 사용자 ID이다. 기록은 표시 번호인 `round`가 아니라 `sessionId`와 `enrollmentId`에 연결한다.

현재 구현은 수강생·회차별 Repository 조회 결과를 조합한다. 데이터 연결을 명확하게 확인할 수 있지만, 수강생과 회차가 늘면 조회 횟수도 증가한다. 이후에는 페이지에 포함된 신청 ID들을 기준으로 기록을 묶어서 조회하는 방식으로 개선할 수 있다.

### 5.3. 미기록·정렬·페이지 처리

- 기록이 없는 회차도 `records`에서 생략하지 않고, `attendance`와 `assignmentStatus`를 각각 `null`로 반환한다.
- 두 상태 중 하나만 기록되어 있으면 다른 상태는 `null`로 유지한다.
- 새 회차가 추가되면 기존 수강생의 조회 결과에도 미기록 칸이 생긴다.
- 회차가 없으면 `sessions`와 각 수강생의 `records`는 빈 배열이다.
- 수강생이 없거나 요청 페이지가 범위를 벗어나면 `content`는 빈 배열이다.
- 범위 밖 페이지에서도 전체 회차와 전체 신청 수 기준의 페이지 정보를 유지한다.
- `page`는 기본 0이며 0 이상, `size`는 기본 20이며 1 이상 100 이하이다. 잘못된 값은 `400`으로 처리한다.
- DB의 회차·신청 일시는 기존 저장 기준에 맞춰 `+09:00` 오프셋을 붙인 ISO-8601 값으로 응답한다.

동시 작업 이후의 인원·기록 비교는 관련 트랜잭션이 모두 종료된 뒤 수행한다. 조회 도착 순서까지 보장하기 위해 대시보드에 신청·취소용 비관적 락을 적용하지는 않는다.

### 6.2. 동시성 테스트 방법과 결과

사용자 생성·승인·로그인·세미나 준비는 동시 실행 구간 전에 완료한다. `runConcurrently()` 도우미를 사용해 요청을 겹쳐 실행하고 모든 응답을 수집한다.

- **정원 경쟁:** 승인된 루키 100명이 각 한 번씩 신청한다. 병렬 작업 수는 32이며, 성공 30건과 정원 마감 70건을 확인한다. SQL로 실제 신청 수, 사용자 중복 여부, 성공한 사용자 집합과 저장된 사용자 집합의 일치까지 검증한다.
- **중복 신청:** 정원 20명의 빈 세미나에 같은 루키가 20회 동시 신청한다. 응답 분포와 DB의 해당 사용자 신청 수를 확인하고, 성공 응답의 신청 ID와 저장된 ID가 같은지 검증한다. 다른 루키가 이후 정상 신청할 수 있는지도 확인한다.

**중복 취소**

'한 사용자가 수강 취소를 10번 수행하면 1번만 반영된다.' 테스트로 같은 사용자의 동시 취소 요청을 검증했다.

정원이 남아 있는 세미나에 루키 두 명이 각각 신청한 뒤, 첫 번째 루키가 자신의 신청을 취소하는 요청 10개를 동시에 보냈다.

첫 번째 취소 요청은 성공해 `204 No Content`를 반환한다. 이후 요청은 이미 신청이 삭제된 뒤 처리되므로 `404 Not Found`를 반환한다.

테스트에서는 응답이 `204` 1건, `404` 9건인지 확인하고, DB에서도 해당 루키의 신청이 0건이며 세미나 전체 신청은 1건인지 확인한다. 처음 신청 2건에서 대상 신청만 한 번 삭제됐음을 검증한다.

취소 요청은 세미나 행 잠금을 획득한 뒤 신청 내역을 조회하고 삭제한다. 먼저 처리된 요청이 잠금을 해제한 후 나머지 요청은 삭제된 신청을 조회하게 되므로, 신청 없음 응답을 받는다.

예상한 상태 코드의 정확한 분포를 비교하므로, `500` 등 다른 상태 코드가 섞이면 정상적인 정원 마감이나 중복 실패로 집계하지 않는다.

**신청·취소 혼합**

정원이 꽉 찬 세미나에서 기존 신청자의 취소와 새 신청자의 신청이 함께 일어날 때, 신청 결과와 DB 상태가 올바른지 확인하는 테스트이다.

정원이 1명인 세미나에 A를 신청시켜 정원을 채운다. 이후, A의 취소 신청과 B의 등록 신청을 `runConcurrently()`로 동시에 실행한다. A의 취소 신청이 먼저 처리되었다면 B의 등록이 성공하고, B의 등록 신청이 먼저 처리되었다면 B의 등록이 실패한다.

취소 응답은 `204`, 신청 응답은 `201` 또는 `409`인지 확인한다. DB에서는 A의 신청이 0건인지 확인하고, B의 신청과 세미나 전체 신청 수가 신청 성공 시 각각 1건, 실패 시 각각 0건인지 검증한다. 최종 신청 수가 정원 1명을 넘지 않는지도 확인한다.

두 처리 순서를 각각 강제하는 방식은 아니며, 실제 동시 실행에서 나온 신청 결과에 맞춰 DB 상태를 검증한다.

테스트는 `TeamEnrollmentConcurrencyTest`의 `신청과 취소가 동시에 일어나도 정원과 신청기록이 일치한다`에 추가되었다. 실행 결과는 [PR #27](https://github.com/minss7/spring-seminar-team2/pull/27)에서 작성자가 보고한 통과 결과를 기준으로 정리했다.

### 6.3. 실제 DB 쓰기 이후의 롤백 검증

실제 MySQL에 기존 기록을 저장한 뒤, Spring이 주입한 서비스를 통해 출석 기록의 생성·수정·삭제를 수행합니다. 이후 `SubmissionRepository`의 특정 조회에서 테스트용 `RuntimeException`을 발생시킵니다.

실패 주입 직전에 같은 트랜잭션에서 SQL로 생성·수정·삭제가 실제 실행된 것을 확인합니다. 예외가 호출자에게 전달된 뒤에는 별도 트랜잭션에서 조회해 모든 기록이 작업 전 상태와 같은지 검증합니다.

수정하려는 값은 다음과 같이 작업 전 상태와 다르게 준비한다.

| 대상 | 작업 전 출석 | 실패를 주입하기 전 수행하는 출석 작업 |
| --- | --- | --- |
| 생성 대상 | 미기록 | `PRESENT` 생성 |
| 수정 대상 | `PRESENT` | `ABSENT`로 수정 |
| 삭제 대상 | `ABSENT` | 기록 삭제 |

검증 순서는 다음과 같다.

1. 별도 트랜잭션에서 작업 전 출석·과제 기록 전체를 읽는다.
2. Spring이 주입한 실제 `SessionRecordService.updateRecords()`를 호출한다. 테스트 메서드 자체에는 `@Transactional`을 붙이지 않는다.
3. 실제 `SubmissionRepository`를 감싼 `@MockitoSpyBean`에서 마지막 대상의 특정 조회 호출에만 실패를 주입한다. 다른 저장소 동작은 실제 구현을 사용한다.
4. 실패를 던지기 직전, 같은 트랜잭션의 `JdbcTemplate` 조회로 출석 생성·수정·삭제가 실제 실행되었는지 확인한다. 이때 서비스 트랜잭션이 활성 상태인지도 검사한다.
5. `RuntimeException`을 상속한 `InjectedFailure`를 던지고, 호출자에게 예외가 전달되는지 확인한다.
6. 서비스 트랜잭션이 끝난 뒤 `TransactionTemplate`으로 새 트랜잭션을 열어 조회한다. 모든 대상의 출석·과제 기록이 작업 전 상태와 동일한지 비교한다.

`observedWrites` 검증으로 실제 쓰기를 확인하는 코드가 실행되었는지도 확인한다. 운영 API에 강제 실패 파라미터나 테스트용 엔드포인트를 추가하지 않았다.

### 6.4. 대시보드 기능 테스트

| 테스트 | 준비와 검증 |

| 루키 한 명이 여러 세미나를 수강해도 데이터가 섞이지 않는다 | Grace Day가 다른 두 세미나에 같은 루키를 신청시키고 서로 다른 기록을 저장한다. 한 세미나에만 다른 수강생도 추가한다. 세미나별 전체 인원, 신청·회차 ID, 사용자 정보, Grace Day, 출석·과제 상태가 올바르게 분리되는지 확인한다. |
| 조회자가 달라도 같은 대시보드 데이터를 반환한다 | 와장·담당 운영진·수강 중인 루키로 같은 대시보드를 조회해 응답 JSON 전체를 비교한다. 실제 수강생 두 명의 사용자 ID와 서로 다른 기록도 확인해 비어 있는 동일 응답으로 통과하지 않도록 한다. |
| 새 회차가 추가되면 기존 기록을 유지하고 미기록 칸을 추가한다 | 기존 두 수강생의 기록을 저장한 뒤 새 회차를 추가한다. 회차 목록이 확장되고 수강생 목록·인원과 기존 회차 기록은 유지되는지, 새 회차의 두 상태는 모든 수강생에게 `null`인지 확인한다. |
